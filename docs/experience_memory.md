# 经验记忆 V0

本版本实现“验证后的记录 → 规则化经验 → 按问题检索 → 模型使用 → 独立评测”。它属于外部经验记忆，不更新模型权重，也不自动改写运行代码。

更有挑战的题目来源、预先分组与开发集基线见 [挑战题评估](challenge_evaluation.md)。

## 如何提炼

`build_experience_memory.py` 默认扫描本机 `results/api_smoke_*`。每题必须有完整 trace、运行汇总和离线评分。数值题需要离线数值检查与运行时最终值验证均通过；净收入题需要数据缺口确认、无数值和无 SQL 执行。网络、认证或业务失败不会被当作正确示范。

当前使用固定模板，从验证过的指标及现行 `METRICS` 合同提炼规则，不让模型任意编写长期政策。已有的三类经验是：

- Order Count 的时间字段、去重粒度和全状态默认口径。
- Customer Payment Value 的 delivered 默认范围、订单粒度聚合及真实表名。
- 净收入缺少必要数据，应保留原指标请求并安全停止。

这一步是将已验证的操作口径固化成可检索经验，不是从几条记录中发现了新的通用推理算法。

## 存储与检索

默认记忆文件是 `memory/experiences.json`，学习报告是 `memory/learning_report.json`。两者都位于本机，被 Git 忽略；需要跨机器保留时单独备份。

每条经验包含规则 ID、适用指标、准确表名、简短操作规则、合同及模板版本、来源任务、trace/评分文件哈希和验证结果。源问题只保存哈希；历史答案金额与完整 SQL 不进入检索提示。同一来源重复导入不会增加重复条目。合同或模板变更后，旧版本保留但不再检索。

指标选择前按中英文关键词检索；SQL 生成前按已解析的指标 ID 检索，每阶段最多三条。结果注入 `relevant_experiences`，当前问题、schema 和指标合同仍优先。原有 schema 检查、只读 SQL、答案校验和安全停止继续执行。

每次运行增加 `memory_retrieved` 事件，记录开关、快照 ID、命中经验及阶段；`llm_request_started` 同时保存完整 messages 和提示哈希，可以核实经验是否真正发给模型。保存的 messages 不包含请求头或 API key。

## 使用

在项目目录执行以下命令。

```bash
# 从已有合格记录建立/更新记忆，无模型请求
.venv/bin/python scripts/data_agent/build_experience_memory.py

# 只导入指定训练来源
.venv/bin/python scripts/data_agent/build_experience_memory.py --run-dir results/<source-run>

# 正常三题运行：默认检索已有记忆，运行和离线评分结束后追加合格来源
.venv/bin/python scripts/data_agent/run_api_smoke.py

# 完全关闭本次记忆读取和写入
.venv/bin/python scripts/data_agent/run_api_smoke.py --no-memory

# 使用指定记忆库
.venv/bin/python scripts/data_agent/run_api_smoke.py --memory-file memory/experiences.json
```

自动学习只发生在离线评分完成后，不改变正在运行的 Agent 的记忆快照。首版面向单进程、本地文件使用；不支持多个进程并发写同一个记忆库。

## 有无记忆对比

```bash
.venv/bin/python scripts/data_agent/run_memory_eval.py --suite v1
.venv/bin/python scripts/data_agent/run_memory_eval.py --suite v2

# 扩展评估：12 道不同问题，每题在两种条件下各运行 3 次
.venv/bin/python scripts/data_agent/run_memory_eval.py --suite v3 --repeats 3
```

v1/v2 每组有四题：订单数、支付金额、多指标连接和净收入停止；每题运行一次，两种条件通常共需要 20 次模型请求。v3 有 12 道不同问题，增加显式 delivered/canceled/全状态范围、默认口径和英文表述；重复三次时共 72 次任务执行，正常需要约 180 次模型请求，JSON 修复可能增加请求数。两组使用相同模型配置和确定性验证，仅经验注入不同；执行先后顺序按题目和重复轮次交替。

每轮在独立 `results/memory_eval_<timestamp>/` 下保存记忆快照、问题清单、每次执行的完整轨迹、参考数值、`comparison.json` 和 `comparison.md`。重复运行的轨迹使用 `EM21_r01` 等独立目录，不覆盖之前的记录。运行期间不追加经验，禁止源问题与评测问题完全相同。所有独立参考 SQL 都在两组运行完成后执行，不进入模型提示。评分时核对快照哈希、题目及记忆开关，并拒绝缺失或重复的配对记录。评测目录不会被默认经验导入脚本扫描。

若发生 API/认证错误，保留已运行的轨迹并将实验标为 `ABORTED`，停止剩余请求；不对未完成的配对实验生成比较结论。修复连接后重新运行会创建新目录。

首轮 v1 中，关闭记忆通过 4/4，启用记忆通过 3/4。失败发生在指标选择阶段：模型输出了不存在的 `payments` 表，被 schema 检查拒绝。开发阶段据此将准确表名加入经验模板，并升级模板版本；旧经验仍留存。随后使用不同月份的 v2 套题复测，不能把对 v1 的调试结果当作独立泛化证据。

本机第二轮 v2 结果为两组均通过 4/4、错误答案接受数均为 0。启用记忆组命中经验 6 次，总 token 从 5,552 增加到 6,622（约增加 19%）。因此本次确认了记忆链路可用，没有证明准确率提升，也没有节约用量。

原始记录：[首轮对比](../results/memory_eval_20261026T050412_175811Z/comparison.md)、[第二轮对比](../results/memory_eval_20261026T051516_185896Z/comparison.md)。这些链接指向本机结果目录，Git 克隆不包含相应运行产物。

比较报告包含通过数、错误答案接受数、请求数、token 用量、延迟和经验命中数。提前失败会减少后续请求，不能误认为节省成本。四题单次运行不足以证明统计意义上的提升；应保留负面结果，并在更大、冻结的测试集上验证效果。

## 准确率之外的指标

新增指标由 `evaluation/memory_metrics.py` 汇总，定义如下：

| 指标 | 定义 | 解释边界 |
|---|---|---|
| 同类错误复发率 | 表名错误次数 / 可回答且已产生成功分析输出的运行次数 | 对应首轮真实出现过的 `payments` 错误；仅覆盖分析/Schema 阶段。更早失败的排除数单独保存，不能把没运行到此阶段算作避免了错误。 |
| 记忆净收益 | （无记忆错而有记忆对的次数 − 无记忆对而有记忆错的次数）/ 配对总数 | 按同题、同重复轮次配对；保留改善、退化、均对、均错四类明细。它描述观察结果，不能独立证明某次随机生成变化的原因。 |
| 每次正确完成的成本 | 所有运行的 Token、请求数或耗时 / 正确完成次数 | 包含失败消耗；正确的数据缺口停止也算正确完成。零次正确完成返回 `null`，不写成成本为 0。 |
| 完整任务耗时 | 从调用 Runner 到轨迹、结果落盘完成的单调时钟耗时 | 包含模型、工具及 SQL，排除离线评分；报告均值和 nearest-rank P50/P95。旧记录没有计时则记为 `null`。 |
| 重复运行稳定性 | 每题通过次数、总次数，以及始终通过、始终失败、结果波动的题数 | 12 题各跑 3 次仍然只有 12 道不同题。始终失败不属于可靠完成。 |

数值不匹配单独记录为离线参考不匹配，不会仅凭错误答案就断言是日期字段、状态筛选或关联倍增导致。所有失败类别和具体运行 ID 都可追溯。错误答案被接受的次数为 0，也不能说明对人为构造错误的拦截率为 100%。

Token 是服务商报告的输入、输出用量，不是实际账单；缓存价格没有计入，服务商未报告的失败请求消耗可能缺失。净收入停止受两组共有的确定性守卫控制，不能单独归功于经验记忆。本轮只评估固定模板经验在同一数据库与指标合同下的复用，不代表模型权重学习或 RSI。

## 本机 v3 重复评估结果

2026-10-26 使用请求模型 `deepseek-v4-flash`，冻结同一记忆快照，12 道不同题在两种条件下各重复 3 次；共完成 72 次任务执行、180 次模型请求。结果见 [v3 比较报告](../results/memory_eval_20261026T053606_027506Z/comparison.md) 和 [完整 JSON](../results/memory_eval_20261026T053606_027506Z/comparison.json)。

| 指标 | 关闭记忆 | 启用记忆 |
|---|---:|---:|
| 正确完成 | 36/36 | 36/36 |
| 表名错误复发 / 可观察机会 | 0/27 | 0/27 |
| 每次正确完成 Token | 1,401.92 | 1,742.64 |
| 每次正确完成请求数 | 2.5 | 2.5 |
| 每次正确完成完整耗时 | 3.55 秒 | 3.71 秒 |
| 单次任务耗时 P95 | 5.56 秒 | 5.84 秒 |
| 三次均通过的不同题目 | 12/12 | 12/12 |

36 对结果中，改善 0、退化 0、均通过 36，记忆净收益为 0。启用记忆覆盖全部 36 次运行，共注入 69 条次经验；总 Token 从 50,469 增加到 62,735（+24.3%），任务累计耗时从 127.80 秒增加到 133.48 秒（+4.4%）。本轮没有观察到正确性、错误复发或调用次数方面的收益，也不能由有限样本断言记忆始终无效。净收入题的正确停止由共有守卫保证；12 道不同题仍不足以证明广泛泛化，耗时也受服务端波动影响。

全部 72 条执行轨迹均留存，记忆库与冻结快照的哈希一致，没有把评测结果写回训练记忆。最初受沙箱网络限制的单次尝试保存在 `results/memory_eval_20261026T053557_153614Z/`，状态为 `ABORTED`，未混入上述对照结果。

## 测试

挑战题增加了另一条显式入口：从已复核的开发集错误及同题正确重跑中构建候选经验，见 [挑战题与候选对照](challenge_evaluation.md)。它使用独立候选文件，仅在相关 SQL 生成时检索；旧指标经验保持原版本，测试集结果不导入。候选规则由代理复核后编写，程序验证证据；这仍是经验检索增强，不是模型权重训练或递归自我改进。

```bash
.venv/bin/python -B -m pytest -c pytest.ini -q -p no:cacheprovider tests/test_experience_memory.py
.venv/bin/python -B -m pytest -c pytest.ini -q -p no:cacheprovider tests/test_memory_metrics.py
```

测试使用临时数据库与脚本化模型，覆盖证据过滤、去重、过期经验隔离、受控文本、真实表名、提示注入、评测隔离，以及离线发现错误连接导致的金额膨胀。脚本化模型测试用于验证实现，不作为真实模型能力提升的证据。

完整回归时，父目录的 `test_olist_data_foundation.py` 使用 session 级 DuckDB 连接，配置与运行时的禁外部访问连接不同，需要放在独立 pytest 进程中：

```bash
.venv/bin/python -B -m pytest -c pytest.ini -q -p no:cacheprovider tests ../tests --ignore=../tests/test_olist_data_foundation.py
.venv/bin/python -B -m pytest -c pytest.ini -q -p no:cacheprovider ../tests/test_olist_data_foundation.py
```
